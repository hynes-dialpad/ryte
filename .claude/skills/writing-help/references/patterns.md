# Editing patterns

Adapted from [petergyang/no-ai-slop](https://github.com/petergyang/no-ai-slop). Apply these
patterns as evidence for a focused edit, not as a claim about who wrote a draft.

## Principles

- Preserve the writer's point, voice, useful edge, and supported detail.
- Lead with the point when setup adds nothing.
- Prefer active voice, direct verbs, concrete mechanisms, and sourced numbers.
- Make the minimum effective edit. Do not flatten every paragraph into the same shape.
- Keep structure when it helps the reader; reorganize only when the artifact is doing the wrong job.

## Patterns to detect

| Pattern                 | Evidence                                         | Focused correction                                  |
| ----------------------- | ------------------------------------------------ | --------------------------------------------------- |
| Throat clearing         | "Here's the thing" or "It's worth noting"        | Start with the point.                               |
| Faux insight            | "What everyone misses"                           | Remove the setup and support the claim.             |
| Importance puffery      | Unsupported "pivotal" or "transformative"        | State the fact and let it stand.                    |
| Weasel attribution      | Unnamed "experts agree" or "studies show"        | Name the source or remove the claim.                |
| Synonym cycling         | Several names for one system or concept          | Repeat the precise term.                            |
| Robotic rhythm          | Repeated openings or identical paragraph shapes  | Vary or combine only where the content warrants it. |
| Rhetorical setup        | A self-answered question or "think about it"     | Make the claim directly.                            |
| Summary-recap ending    | A final paragraph only repeats the artifact      | End with the result or next action.                 |
| Decorative formatting   | Emoji, scattered bold, or sections without a job | Let the information determine structure.            |
| Abstract nominalization | A noun hiding who does what                      | Name the actor and action.                          |
| Tangled sentence        | Several independent claims joined together       | Split by idea without removing supported nuance.    |

## Technical-writing exceptions

- Preserve product and project names as proper nouns.
- Preserve exact negative constraints, ownership boundaries, unsupported behavior, and failure modes.
- Preserve lists that encode real options, validation rules, mappings, or ordered procedures.
- Preserve hedging when the source is genuinely uncertain.
- Preserve code identifiers, paths, commands, issue keys, version numbers, citations, and formal contract language unless source evidence proves them wrong.

## Final check

Confirm the result preserves supported facts and constraints, leads with what the reader needs,
uses consistent terms and concrete actions, avoids decorative structure, and sounds natural to a
technical colleague.
